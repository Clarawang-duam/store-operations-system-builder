# 业务规则卡

| 问题 | 填写内容 |
|---|---|
| 谁从哪里发起？ | 操作入口、角色、门店或资源的访问范围 |
| 什么情况下可以做？ | 当前状态、资源条件、业务口径 |
| 成功后发生什么？ | 金额、状态、写入及必须一起成立的结果 |
| 哪些业务不变量必须成立？ | 写成能断言的约束，例如「每笔预约最多生成一笔营业订单」。注明适用条件和观察位置。 |
| 失败和重试怎么办？ | 已写入内容是否回滚、如何继续、重复请求的结果 |
| 怎么证明做对了？ | 不变量、初始数据、操作、预期与观察结果、命令或入口、运行环境、未覆盖的情况 |

## 示例：预约核销并开台

手作工坊的交接记录里，旧流程会先标记「已到店」，再尝试开台。座位不可开时，预约已变更，换座重试也会失败。项目修复是先开台成功，再更新预约状态。下表把这个案例扩展成一份可移植的设计示例，具体保护措施按项目数据模型选择。

| 问题 | 示例答案 |
|---|---|
| 谁发起？ | 有本店营业权限的店员，在预约记录中选择套餐与座位后提交。 |
| 前置条件 | 预约属于本店且待核销。座位可用，容量满足要求。写入时再次确认这些条件。 |
| 成功 | 生成一张营业订单、占用对应座位、保存预约与订单的关联，并标记已核销。 |
| 业务不变量 | 在尚未开台且因座位占用被拒绝时，已确认预约保持原状态，既有座位不变，这次操作不生成订单。同一预约最多生成一笔营业订单；核销成功后，订单、座位与预约对应。 |
| 部分失败 | 同库实现应使这组变更一起提交。任何一项失败时保留原预约状态，店员可以换座重试。 |
| 重复和并发 | 对同一预约重复提交时返回已有结果或明确提示已处理。两笔不同预约争用同一座位时，至多一笔成功。 |
| 验收 | 正常路径核对订单、座位及预约。选已占座位再换座。模拟写入中途失败，核对各表无半成品。并发提交后检查是否仅产生预期订单。 |

## 实际验收记录

来源：手作工坊项目。测试调用真实的 `checkInReservation` 业务函数及状态机，用替身模拟仓储、开单和支付等依赖。测试数据为合成数据。

| 初始数据和操作 | 必须观察到的结果 | 实际结果 |
|---|---|---|
| 已确认预约，选择已占用的座位 | 返回改选空闲座位的提示。预约仍为 `CONFIRMED`；预约、座位、订单写入均未触发。 | 通过。 |
| 保留同一预约，改选空闲座位 | 仅调用一次开台，且座位参数是新选的空闲座位。预约依次走到 `CONVERTED`，返回开单结果。 | 通过。 |

在手作工坊仓库运行以下命令。Vitest 退出码为 0，两个测试文件共 5 项通过，其中 1 项覆盖上述失败和重试流程。

```sh
npm test -- src/domains/reservation-check-in.test.ts src/engines/state-machine-engine.test.ts
```

本次证据覆盖业务层的分支、状态和调用次数。真实数据库中的订单行数、座位落库、部分写入回滚、重复提交与并发争抢还需集成测试。当前源码在开单后分步推进预约状态，以上测试不能证明整个流程具备原子性。
